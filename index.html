The frontend model

              
UI = F(state)

              

                A component declares the data it needs as a query. That query stays alive. Every
                write updates its result before the next frame. No cache invalidation, refetch
                choreography, or hand-written synchronization.
              

              

                01 query once→
                02 write state→
                03 every view is current

01 · queryrecent writes

                
const recent = q.shape
  .where(exists(
    onLayer,
    (l) => l.where.visible(1)
  ))
  .orderBy("updated", "desc")
  .limit(8)
  .materialize();

              

              

                
01 / Declare the view

                
The query is the component’s data contract.

                

                  “Recent writes” does not fetch eight rows and leave you holding a snapshot. It
                  creates a maintained view: the newest eight visible shapes, in order, for as
                  long as the component needs it.
                

                
On the canvas The “recent writes” panel is bound to this exact query.

              

            


            

              

                
02 · readcomponent

                
function RecentWrites() {
  return recent.data.map((shape) =>
    row(shape.id, shape.kind, shape.updated)
  );
}

              

              

                
02 / Render current state

                
The UI is just a function of the view.

                

                  The component reads the query’s current rows. The binding schedules a render
                  when that view folds a delta; application code does not work out what changed
                  or patch the collection by hand.
                

                

                  Loading the initial result and maintaining it are the same abstraction. Once
                  materialized, recent.data is the answer now.

03 / Change state once

                
A write is the only update path.

                

                  Dragging a shape writes a row. Inside that same call, the engine derives the
                  consequences and folds them into every affected view. When the promise resolves,
                  the next paint already has the right data.
                

                

                  The write does not know which components exist. The components do not know why
                  the row changed. That missing coordination code is the point.
                

                
Try it Drag a shape and watch the query panels pulse together.

const palette = q.shape

const largest = q.shape

const recent = q.shape
  .orderBy("updated", "desc").limit(8);

const cell = q.shape
  .where.c1(cellId).orderBy("z", "asc");

              

              

                
04 / Let queries do the bookkeeping

                
One row can have many derived consequences.

                

                  Recoloring moves a count between palette groups. Resizing can reseat the
                  leaderboard. Any edit moves the shape to the top of the feed. Dragging across a
                  cell boundary removes it from one canvas query and inserts it into its neighbor.
                

                

                  These are not four update handlers. They are four declarations, each maintained
                  from the same write stream and charged only for the delta that touched it.
                

              

            


            

              

                
05 · relatelayer visibility

                
const visible = exists(onLayer,
  (layer) => layer.where.visible(1)
);

const painted = q.shape
  .where(visible)
  .orderBy("z", "asc");

await store.write((tx) => {
  tx.edit("layer", hidden, visibleLayer);
});

              

              

                
05 / Model relationships, not effects

                
A tiny write can have a large, exact fan-out.

                

                  Visibility lives on one layer row. Painted queries reach it through a
                  relationship. Hide the layer and one row changes; every dependent query sheds
                  precisely the shapes that no longer qualify.
                

                

                  You do not walk the shapes, clear caches, or notify panels. The join already
                  describes the consequence.
                

                
On the canvas Click an eye in “layers” to make one write fan out across thousands of rows.

              

            


            

              

                
06 · keep identityselection

                
const selected = q.shape
  .where(exists(onSelection))
  .orderBy("z", "asc")
  .materialize();

// Selecting changes data, not the query.
await store.write((tx) => {
  tx.add("selection", { shape: id });
});

              

              

                
06 / Change data, not query identity

                
Even ephemeral UI state can be declarative.

                

                  The selected ids live in a table. The selection query is registered once and
                  never changes. Brushing a marquee writes only the rows crossing its edge, and
                  the fixed query folds those deltas.
                

                

                  Put ids into query arguments instead and every pointer move creates a different
                  query that must hydrate again. The useful question is simple: did the question
                  change, or did the data change?
